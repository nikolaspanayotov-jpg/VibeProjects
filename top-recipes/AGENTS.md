# Top Recipes

Live URL: https://nikolaspanayotov-jpg.github.io/VibeProjects/top-recipes/

This project is a recipe notebook and Monday–Sunday planner. Follow the repository's root AGENTS.md and frontend-design skill. Keep all changes inside `top-recipes/`.

## Run and publish

There is no application build step. Serve this folder, or the repository root, with any static server. `python3 -m http.server 8000` is enough. GitHub Pages publishes this folder from `main` at the URL above. Keep the folder name and all asset URLs relative.

Opening `index.html` from disk loads the classic scripts normally. Local browser security blocks fetching Markdown automatically from disk, so use Open recipes.md to select the collection. On HTTP and GitHub Pages, the page fetches recipes.md automatically.

## Architecture

- `recipes.md` is the sole recipe content source. Edits appear after publishing and refreshing; no generated recipe JSON exists.
- Recipe YAML may include `image: assets/recipes/<slug>.svg`. All current dishes have individual artwork assignments; the original three retain `assets/breakfast.svg`, `assets/lunch.svg` and `assets/dinner.svg` respectively. Never choose artwork by meal category. `validRecipeImagePath` accepts only local asset paths, and `recipeIllustration` is shared by cards, details and pickers with a one-time load-error fallback to `assets/recipe-placeholder.svg`. That neutral place setting also covers recipes without an image. Image changes need no code registry or build step.
- `vendor/` contains local Marked 15.0.12 and js-yaml 4.1.0 browser distributions with their licenses.
- `src/content.js` validates Marked tokens and YAML metadata. Never render authored content as HTML.
- Classic scripts load with `defer`, in the order in index.html. They expose helpers through `globalThis.TopRecipes`; each file has its own function scope.
- `src/app.js` coordinates the library, pickers and planner. `experience.js` renders saved-week and portion/leftover controls; `planner.js` contains pure calendar, meal-edit, settings-remapping and cooking-batch functions; `storage.js` validates persisted data; `recipes.js` renders ingredients and recipes; `capture.js` manages screenshot mode and print; `export.js` prepares measured canvas PNGs and native file sharing; `cooking.js` manages the separate cooking dialog, session steps and timers.
- The entire recipe library is an accessible disclosure controlled by `#recipes-toggle` and `#recipes-content`. At widths up to 960 px it defaults closed, matching the CSS breakpoint for the stacked workspace; desktop defaults open. Keep those breakpoints aligned. Preserve search/filter DOM when closing, expose total recipe count outside the disclosure, and return focus to a visible control. The expanded library header stays sticky. Closing from its bottom returns focus and scroll to the planner; closing a sticky header after a long scroll brings the compact collection back into view. An explicit choice survives resizes for this page visit, with no new storage key. Collapsing also gives the desktop planner the full width.
- `src/shopping.js` scales batches by household and individual meal servings, combines linked leftovers into the original cooking batch, groups by grocery aisle, merges equivalent ingredient names with matching units, converts kg/g and l/ml, and exposes weekly tick selections and quantity controls. Preparation notes remain available through Recipe amounts. Do not combine different foods or convert volume to weight without ingredient-specific data. Pantry quantities (“to taste”, pinches, unspecified amounts) default to one pack; whole items round up.
- `styles.css` contains the cream/olive/terracotta visual system, mobile planner and portrait capture layout. Fonts and illustrations are local or system-provided.

Do not rename shipped storage keys `top-recipes:planner:v1` or `top-recipes:ingredients:v1`, recipe IDs or ingredient IDs. Preserve malformed saved data until the user explicitly resets it. Calculate dates in local time. Moving a grid meal into an occupied slot swaps the meals; adding from the library replaces the target. Undo remains available beside Clear week even if its toast is dismissed.

The planner JSON retains string/null recipe IDs in its original `weeks` shape. Optional `preferences` contains `{ householdSize: null|1..24, favourites: recipeId[], recent: recipeId[] }`; null preserves full authored batches for legacy plans. Recent keeps at most 12 IDs. Optional `mealSettings[localMonday][day-meal]` contains `{ servings?: 1..100, leftoverOf?: day-meal }`. Only link to an earlier fresh slot with the same recipe. `cleanMealSettings` removes invalid links; `moveMealSettings` carries portions and remaps links during swaps. Affected remaining meals cook fresh if their source is removed, replaced or moved too late; announce it. Replacing a recipe resets that slot’s settings. `cookingBatches` sums the portions eaten at the source and all linked meals, then divides by the recipe yield. Do not interpret source portions as including leftovers already. Undo restores both week and meal settings.

Optional `templates` is an array of up to 50 `{ id, title, week, settings }` records. Copy last week and template apply clone meal/settings data, with Undo, leaving weekly shopping edits and household preferences alone. Never write defaults on page load. Pins and recents use the existing planner key. Keep mobile navigation, library collapse and CSS aligned at 960 px; hide navigation in dialogs and print, and reserve safe-area space at the bottom.

Shopping edits live in the existing planner JSON as optional `shoppingWeeks[localMonday][ingredientKey]` records `{ baseline, quantity, selected, bought?: boolean }`. Accept old planner records without this field. Preserve selections when the plan changes, and keep manual quantities and bought marks only while their calculated baseline is unchanged. Include checkboxes and Bought checkboxes are independent; shopping mode hides editing controls and optionally hides bought items. Reset list restores selected quantities and clears bought marks for one week; it does not alter meal placements or recipe checkboxes. The existing capture dialog supports both the meal grid and selected shopping items, paginating shopping screenshots with a 5–10 row-height budget according to viewport height and reserving room for aisle headings. Screenshots include all selected positive-quantity items with their bought marks, even when hidden in shopping mode. Hiding controls must not change page boundaries. Printing the shopping capture includes every selected item.

Custom groceries live in optional `customShoppingWeeks[localMonday]` arrays of up to 200 `{ id, name, quantity, unit, aisle, selected, bought }` records. `SHOPPING_AISLES` and `EXTRA_UNITS` are shared constants exported by storage.js before shopping.js loads. `saveShoppingState` writes recipe edits and extras together to the existing planner key. Custom row keys use `extra:<id>|<unit>`; never merge them into recipe totals or apply household scaling. Qty and Bought edits update the custom record, not `shoppingWeeks`. Reset list preserves extras and their quantities but resets their include/bought choices. Copying a week or applying a template never copies extras. Clear removal undo and any custom edit form when changing weeks.

`export.js` uses Canvas 2D with system fonts and a measured text layout at 1080 px wide, wrapping full names and growing the image height. No HTML capture library or external assets are needed. Plan images include all 21 slots; shopping images match the current capture page, with aisle headings, quantities, extras and bought marks. Prepare and cache the PNG File before enabling Save/Share so Web Share retains the tap’s user activation. Generation tokens discard stale encodes after page changes or close. Show Share only when `navigator.canShare({ files })` supports the actual file. Cancellation must not trigger a download. PNG failure leaves screenshot and Print controls usable. Revoke download object URLs after use; create the download anchor within the modal. Hiding controls never changes page boundaries.

`cooking.js` keeps step/ingredient ticks and timers in memory per recipe for the current page visit. These preparation checks do not write recipe purchase checks or planner data. Display the authored recipe yield clearly. Timers use deadlines and elapsed time, not interval tick counts; completion alerts are visible in the dialog and announced once. Pause all timers and clear the interval on close; reopening the recipe restores paused progress. A user-selected screen wake lock is optional, released on close, and must handle unsupported/denied requests without breaking cooking mode. Never request notification permissions or imply a background audible alarm.

## Verification

Development dependencies belong only in `tests/`: run `npm ci --prefix tests`, then `npm test --prefix tests`. The tests load the same vendored parsers and classic scripts that ship to Pages. Verify the page, script, stylesheet and recipes.md URLs after publication. Check 390 px and desktop layouts in a real browser when preview infrastructure is available; DOM tests do not prove visual fit or native gesture behavior. The development-only native canvas package checks actual PNG encoding and geometry; inspect representative exported images alongside the tests. Real mobile file sharing and wake-lock behavior still need browser checks when infrastructure is available.

Commit messages start with `top-recipes:`. Only push to main after the relevant checks pass.
