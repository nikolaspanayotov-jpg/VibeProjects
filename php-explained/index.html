01 / Before the bug

A website has a backstage.

You see a page. Behind it, a server receives your request, does some work, and sends a response. PHP is software many servers use to do that work.

01

You ask for something

You open a page or submit a form. Your browser sends a message called a request.

02

PHP uses a working desk

A server worker handles the request. Its temporary memory is like a desk holding papers while a task is in progress.

03

The desk gets cleared

The response goes back. Temporary memory is released for reuse. A worker may stay alive to serve another request.

The rule that matters: once a piece of memory is released, PHP must stop treating it as if it still contains the old, valid information. And unfinished information must never be treated as finished.

Where does the desk analogy stop being accurate?

Computers do not read loose notes like people. PHP’s underlying native code uses addresses and structured data. If it reads an invalid address or treats uninitialized bytes as a valid structure, it may crash or follow unintended execution paths. Turning that into code execution requires carefully controlled conditions. The colored boxes here illustrate bookkeeping errors; they do not show a working exploit.

What do the actual patches change?

For the out-of-memory flaw, PHP replaces an abrupt jump out of an operation with a controlled failure at a safe execution point, or an immediate process exit at a higher memory threshold. This avoids running ordinary cleanup on an invalid intermediate state. For the stale-state flaw, the fixes address retained request references and their lifecycle. The key idea is to prevent later work from using memory that is no longer valid. See the two technical advisories.

03 / Why that becomes dangerous

A crash is bad.
Control is worse.

Most software errors do not hand over control. Here, researchers showed that carefully arranged memory could turn invalid bookkeeping into remote code execution.

“Remote code execution” in everyday language

An outsider sends messages over the network that make the server run instructions they chose. “Unauthenticated” means they may not need an account or password. It does not mean every request succeeds.

What could an attacker actually do?

Run code with the permissions of the PHP worker. That could expose data or secrets the worker can access, alter a site, or interrupt service. It does not automatically grant administrator access to the whole machine. The impact depends on the worker’s permissions and isolation.

Why wouldn’t a login screen stop it?

Some PHP processing happens before the website’s own code or login checks. The PHP team demonstrated such an attack against Apache’s mod_php setup. Other environments have different conditions; a login screen cannot be treated as a fix.

Same family of mistake. Different sequence.

CVE-2026-109618: stop halfway through preparing data → cleanup trusts the unfinished data.

CVE-2026-109619: release a request’s memory → keep an old reference → a later request on the same worker uses it too soon.

The two flaws need not be chained together. Memory disclosure is also a possible outcome in affected conditions. Severity describes potential impact, not a guarantee that every installation is exploitable.

04 / Put it in context

What does this mean for me?

PHP is used by many sites and products, including systems built on WordPress, Drupal and Joomla. A product name alone cannot establish whether a particular deployment is vulnerable.

Check a PHP version

Educational check for the original two flaws only. This does not scan a website, verify a patch, or assess the October 23 issue.

Why updating the website itself may not be enough

PHP is the engine underneath the application. Updating a theme, plugin, or CMS does not necessarily update that engine. Ask the hosting provider about the PHP runtime and all deployed instances, including containers and background services. Vendor packages sometimes include backported security fixes without changing to PHP’s upstream version number.

Do temporary workarounds solve it?

The PHP team says updating is the complete solution for the original two flaws. Configuration changes can close particular paths, but are not universal fixes. Administrators should follow the official advisory, assess operational tradeoffs, restart affected workers as instructed, and verify the running deployment. A firewall or a hidden error message alone does not establish safety.

October 23 update: a separate, narrower issue

CVE-2026-115560 concerns session upload progress under an unusual combination of configuration and application behavior. The application must change its session serialization handler at runtime in the way PHP describes. The October 21 patches do not address this separate issue.

PHP recommends administrators disable session.upload_progress.enabled until the next regular bugfix release; applications that never change the serialization handler at runtime can keep it enabled. This is an administrator task. Read the October 23 PHP advisory for the exact conditions and current guidance.

06 / Your take-home explanation

The 30-second version.

Use this when someone asks, “So what actually happened?”

“PHP helps websites handle visitors’ requests. Two bugs meant it could trust unfinished data or keep using a reference to memory it had already released. Researchers showed that an attacker could exploit those mistakes to make a server run their instructions, sometimes without logging in. Website operators need to update PHP and check the latest advice from their provider.”

A small glossary

Server: a computer that answers requests. Runtime: the software that runs application code. Worker: a process doing server tasks. Memory: temporary working space, different from saved files. Reference / pointer: a way to locate data in memory. Use-after-free: using memory after it has been released. Patch: a software repair. CVE: an identifier for a publicly tracked security flaw. Backport: a security repair applied to an older software branch.
